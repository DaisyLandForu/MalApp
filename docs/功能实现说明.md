> 告诉我，我现在有两个引擎的输出并且有些冲突样本已经人工标注好，以及已经确定的好的武汉接口的一些恶意APP样本和白样本，我应该如何划分数据集，验证集和测试集呢，验证集调节什么参数，是怎么调节的，不能使用网络或者机器学习调节吗或者不能用这些数据调节大模型的参数吗

建议你把现在的数据分成三层来用，不要一上来就全部混在一起调规则。

**1. 先定义“最终标签来源优先级”**

建议按可信度排序：

1. 人工标注冲突样本
   最高优先级。因为这是专门针对两个引擎不一致的难样本做过判断。

2. 武汉接口已确认恶意 APP / 白样本
   作为高置信黑白样本，但要记录来源字段，例如 `label_source=武汉已知黑/白`。

3. 两个引擎一致样本
   可以作为弱标签或辅助评估，不建议直接当强标签，除非后续人工抽查过。

4. 两个引擎冲突但未人工标注
   暂时不要进训练/验证/测试，只进“待标注池”或“灰样本池”。

最终你需要形成一张统一样本表，至少包含：

`md5`、`appName`、`pkgName`、`size`、`signature/cert`、`engine_360_result`、`engine_cm_result`、`engine_360_score`、`engine_cm_score`、`wuhan_label`、`manual_label`、`final_label`、`label_source`、`sample_group_key`。

其中 `final_label` 建议统一成：

`恶意` / `白样本` / `疑似或灰样本` / `无效样本或不可安装分身包`

像你说的 `MOMO陌陌5/6/7` 这种，最好不要简单归白，也不要归恶意，建议单独设为：

`无效样本/360分身导出包`

这样后面评估时可以单独统计，避免污染恶意识别指标。

**2. 数据集怎么划分**

推荐按 70% / 15% / 15%：

- 训练集：70%
- 验证集：15%
- 测试集：15%

但重点不是比例，而是“不能泄漏”。

你不能简单按 MD5 随机切分，因为同一个 APP 家族、同一个分身包、同一个签名证书、同一个包名变体可能会同时出现在训练集和测试集里。这样测试结果会虚高。

更稳妥的划分方式是按组切分：

`sample_group_key = pkgName + signature_md5`

如果没有完整字段，可以退一步用：

`规范化应用名基础名 + pkgName`
或
`规范化应用名基础名 + cert/signature`
或
`同一分身基础名`

例如：

`MOMO陌陌1`、`MOMO陌陌2`、`MOMO陌陌7` 必须放在同一个集合里，不能一部分训练、一部分测试。

建议：

- 武汉已知黑白样本：按组切分进训练/验证/测试
- 人工标注冲突样本：重点保留一部分进测试集，因为它们是最能检验规则鲁棒性的难样本
- 360 分身导出包：单独分层抽样，训练/验证/测试都可以有，但同一基础名必须在同一集合

更具体一点：

| 数据类型 | 建议用途 |
|---|---|
| 武汉确认恶意样本 | 训练、验证、测试都可用 |
| 武汉确认白样本 | 训练、验证、测试都可用 |
| 人工标注强冲突样本 | 测试集优先保留，少量进验证 |
| 人工标注弱冲突样本 | 验证和测试都要有 |
| 未标注冲突样本 | 不进训练/验证/测试 |
| 360 分身导出包 | 单独类别或排除项，不要混成恶意/白 |

**3. 验证集调什么参数**

验证集不是用来训练最终模型的，它是用来选择规则、阈值、权重的。

你现在更像是在做“多源研判融合”，验证集可以调这些东西：

1. 分数阈值
   例如移动 API `score >= 90` 是否判疑似恶意，`score >= 95` 是否判恶意。

2. 引擎权重
   例如：
   - 360 判恶意 + 移动判恶意：直接恶意
   - 360 白 + 移动 93：如果命中分身规则，则不判恶意
   - 360 恶意 + 移动疑似：是否降为疑似，还是判恶意

3. 白样本优先级
   如果武汉接口确认白样本，但移动 API 给 93，要不要以武汉白样本覆盖移动评分。

4. 黑样本优先级
   如果武汉接口确认恶意，即使 360 或移动给低分，是否仍判恶意。

5. 分身包规则
   例如：
   - 安装名末尾数字
   - 同一基础名出现多个数字后缀
   - APK 大小明显小于正常版本
   - 不可安装
   - 360 分身特征

6. 疑似样本策略
   是保守判白、判疑似，还是进入人工复核。

调节方法可以很简单：

先写一套规则，然后在验证集上看：

- 恶意召回率：真正恶意里你抓住多少
- 白样本误报率：真正白样本里你误杀多少
- 冲突样本准确率
- 360 分身包误判率
- 需要人工复核的比例

然后调整阈值和规则，直到达到业务目标。

比如反诈场景通常宁可多进人工复核，也不要把高危恶意漏掉；但如果是拦截安装，就必须严格控制白样本误报。

**4. 测试集干什么**

测试集只能最后用一次或少量几次，用来回答：

“这套规则/模型在没见过的数据上到底表现怎么样？”

测试集不能用来反复调参数。否则你相当于把测试集也训练进去了，结果会虚高。

测试集建议单独统计：

- 全量准确率
- 恶意召回率
- 白样本误报率
- 冲突样本准确率
- 武汉确认样本准确率
- 分身包识别准确率
- 两引擎不一致场景下的正确率

**5. 能不能用机器学习或网络调节？**

可以用机器学习，但要看数据量和标签质量。

如果你现在有足够多的高质量标签，比如几万条以上，并且字段稳定，可以训练一个轻量模型，例如：

- 逻辑回归
- XGBoost / LightGBM
- 随机森林
- 简单规则评分器

输入特征可以是：

- 360 类型、病毒名、分数
- 移动类型、病毒名、分数
- 武汉接口标签
- appName 特征
- pkgName 特征
- size
- 权限数量
- 高危权限数量
- 是否不可安装
- 是否分身包
- 是否命中仿冒字段
- 是否有动态通联
- 是否有境外通联
- 是否有高危 SDK
- 签名是否异常
- 包名是否随机

但我不建议一开始就直接上复杂模型。你现在的问题里有很多“业务规则非常明确”的情况，比如 360 分身导出包，这类先用规则处理更可靠。

比较推荐：

第一阶段：规则系统
第二阶段：规则 + 轻量机器学习排序
第三阶段：大模型只做辅助解释和人工复核提示

**6. 能不能用这些数据调大模型参数？**

原则上可以，但我不建议你现在直接微调大模型参数。

原因：

1. 你的任务不是纯文本分类
   APP 研判依赖结构化字段、引擎分数、签名、大小、安装状态、接口标签。传统模型或规则更可控。

2. 标签还在变化
   你刚刚就新增了“360 分身导出包”的判断规则。标签体系没稳定前微调大模型，容易把错误逻辑学进去。

3. 样本泄漏风险高
   同一 APP 家族、同一分身基础名、同一签名证书很容易跨集合泄漏。

4. 大模型微调成本高，可解释性弱
   你很难解释为什么某个样本被判恶意，而反诈研判通常需要可追溯理由。

更好的用法是：

- 不调大模型参数
- 把规则、字段、样本证据喂给大模型
- 让大模型输出“研判理由”和“是否需要人工复核”
- 最终判定仍由规则/轻量模型控制

也就是：

规则/模型负责判定，大模型负责辅助分析和解释。

**推荐方案**

你现在最稳的路线是：

1. 建一张统一标注表，合并人工冲突标注、武汉已知黑白样本、两个引擎输出。
2. 设定标签优先级：人工 > 武汉确认 > 双引擎一致 > 单引擎结果。
3. 单独标记 `360分身导出包/不可安装样本`，不要混入普通恶意/白样本。
4. 按 `pkgName + signature` 或应用基础名分组切分训练/验证/测试。
5. 用验证集调规则阈值、引擎权重、分身识别规则、人工复核阈值。
6. 最终只用测试集评估，不用测试集继续改规则。
7. 暂时不要微调大模型，先做规则 + 可解释评分体系。

> 超参数可以通过神经网络反向传播学出来吗

可以，但要分清两类“参数”。

**1. 普通模型参数可以反向传播学出来**

神经网络里的权重、偏置、embedding 等，是标准可学习参数，可以通过反向传播更新。

例如：

```text
输入特征 -> 神经网络 -> 恶意概率
```

网络里的权重会通过损失函数自动学习。

**2. 很多超参数不能直接靠普通反向传播学出来**

传统意义的超参数包括：

- 学习率
- batch size
- 网络层数
- 隐藏层维度
- dropout 比例
- 正则化系数
- 阈值，比如 `score >= 93 判疑似`
- 规则权重，比如 360 权重 0.6、移动权重 0.4

这些通常不是普通训练过程自动学出来的，而是用验证集调。

原因是很多超参数不在可微计算图里，或者是离散选择，比如层数、树深度、是否启用某条规则。

**3. 有些“超参数”可以改造成可学习参数**

比如你现在的场景：

```text
最终风险分 = w1 * 360分数 + w2 * 移动分数 + w3 * 武汉标签 + w4 * 分身包特征
```

这里的 `w1、w2、w3、w4` 可以设计成模型参数，让神经网络或逻辑回归通过反向传播学出来。

再比如判定阈值：

```text
risk_prob = sigmoid(score - threshold)
```

如果把 `threshold` 放进可微公式里，它也可以作为可学习参数。

但如果你的规则是：

```text
if appName 末尾是数字:
    判为分身包
```

这种硬规则本身不可微，不能直接靠反向传播学习。你可以把它变成一个二值特征：

```text
is_clone_suffix = 0 或 1
```

然后让模型学习这个特征的权重。

**4. 神经网络也不能“免费”替代验证集**

即使你把部分超参数设计成可学习参数，也仍然需要验证集。

训练集负责学习参数。
验证集负责选择模型结构、阈值、规则方案、是否过拟合。
测试集负责最终评估。

如果你把所有东西都在训练集上学，包括规则、阈值、模型结构，很容易过拟合。尤其你这种 APP 样本有大量同源样本、分身样本、同签名样本，泄漏风险很高。

**5. 对你这个 APP 研判任务的建议**

可以学：

- 两个引擎分数的权重
- 武汉黑白样本标签的权重
- 是否分身包的权重
- 权限数量、通联数量、境外通联、签名异常等特征权重
- 最终恶意概率模型

不建议直接学：

- 是否使用某条业务规则
- 分身包规则本身
- 人工标签优先级
- 测试集阈值
- 大模型内部参数

比较稳的做法是：

```text
人工/武汉标签 -> 建最终真值
两个引擎输出 + APP结构化字段 -> 训练轻量模型
验证集 -> 调阈值和复核策略
测试集 -> 只做最终评估
```

所以答案是：**一部分可以通过反向传播学出来，但传统超参数通常不能直接学；可以把某些规则权重、阈值改造成可学习参数，但仍然需要验证集来调方案和防止过拟合。**

> 四个智能体的输出分数是根据特征加分得到的，而且分数是自己设置的然后再输出给引擎C，能否将这些加分设置成可学习的参数呢，然后反向求导得到合适的值

可以，且这比直接微调大模型更适合你现在的场景。你可以把“四个智能体的特征加分规则”改成一个**可学习的线性/广义线性评分器**，用人工标注和武汉确认黑白样本来学习每个特征的权重。

核心形式可以是：

```text
risk_logit =
  b
  + w1 * 特征1
  + w2 * 特征2
  + w3 * 特征3
  ...
  + a1 * 智能体1原始分
  + a2 * 智能体2原始分
  + a3 * 智能体3原始分
  + a4 * 智能体4原始分

risk_prob = sigmoid(risk_logit)
```

然后用标签：

```text
恶意 = 1
白样本 = 0
分身/不可安装 = 可单独一类，或先排除
```

通过反向传播学习 `w1, w2, ...` 和 `a1, a2, a3, a4`。

**怎么改造**

你现在如果是这样：

```text
命中高危权限 +10
命中境外通联 +15
疑似仿冒 +20
移动API 93分 +30
```

可以改成：

```text
score = sigmoid(
    b
  + w_high_perm * high_perm_hit
  + w_foreign_net * foreign_net_hit
  + w_fake_app * fake_app_hit
  + w_cm_93 * cm_score_93_hit
)
```

其中：

```text
high_perm_hit = 0/1
foreign_net_hit = 0/1
fake_app_hit = 0/1
cm_score_93_hit = 0/1
```

这些 `w_*` 就是可学习参数。

连续特征也可以用：

```text
score_360 / 100
score_cm / 100
permission_count
dynamic_url_count
foreign_domain_count
apk_size_mb
```

但最好先做归一化，不然大数值特征会压过其它特征。

**能不能反向求导**

可以，只要你的评分公式是可微的。

可微：

```text
加权求和
sigmoid
softmax
均方误差
交叉熵损失
```

不可微或不适合直接求导：

```text
if/else 硬规则
字符串匹配
正则判断
分组去重
是否末尾数字
是否同一基础名
```

不过这些不可微规则可以先变成特征：

```text
is_clone_suffix = 1/0
same_base_name_count = 数值
is_uninstallable = 1/0
size_ratio_abnormal = 1/0
```

然后让模型学习它们的权重。

**四个智能体可以怎么接**

有两种方案。

第一种：学习最终融合权重，最简单稳妥。

```text
final_logit =
  b
  + a1 * agent1_score
  + a2 * agent2_score
  + a3 * agent3_score
  + a4 * agent4_score
  + w_clone * is_clone_suffix
  + w_wuhan_mal * wuhan_malicious
  + w_wuhan_white * wuhan_white
```

这样四个智能体内部规则暂时不动，只学习“谁更可信”。

第二种：学习每个智能体内部特征加分。

```text
agent1_score = w11*f11 + w12*f12 + w13*f13
agent2_score = w21*f21 + w22*f22 + w23*f23
agent3_score = w31*f31 + w32*f32 + w33*f33
agent4_score = w41*f41 + w42*f42 + w43*f43

final_score = sigmoid(agent1_score + agent2_score + agent3_score + agent4_score + b)
```

这个更细，但前提是你能把每个智能体命中的特征都结构化记录下来。

**验证集调什么**

训练集用于学习这些权重。
验证集用于调这些东西：

- 最终判恶意阈值，例如 `prob >= 0.8`
- 判白阈值，例如 `prob <= 0.2`
- 中间区域是否进人工复核
- 正则化强度，例如 L1/L2
- 是否启用某类特征
- 是否把分身包单独排除
- 类别权重，例如更重视恶意召回还是白样本误报

例如：

```text
prob >= 0.85 -> 恶意
prob <= 0.15 -> 白样本
中间 -> 人工复核
分身包命中 -> 无效/分身包，不进入恶意判定
```

**注意点**

不要让同一 APP 家族、同一签名、同一分身基础名同时出现在训练集和测试集。否则学出来的权重会看起来很好，但实际泛化差。

另外，武汉确认黑白样本和人工冲突样本的分布可能不同。建议训练时保留 `label_source`，评估时分别看：

- 武汉黑样本召回率
- 武汉白样本误报率
- 人工冲突样本准确率
- 分身样本误判率

**结论**

可以把加分项改成可学习参数，并通过反向传播得到更合适的权重。建议先从“逻辑回归/浅层神经网络”开始，而不是复杂大模型：

```text
结构化特征 + 四个智能体原始分
-> 可学习加权模型
-> sigmoid/softmax
-> 交叉熵训练
-> 验证集选阈值
-> 测试集最终评估
```

这条路线可解释、可控，也更容易向业务方说明每个特征为什么影响最终分数。

> 假如在一开始训练集训练的时候，恶意怀疑和良性的阈值就不合理怎么办，现在找到更好的超参数是用验证集，网格搜索的方法，是否有更好的方法来搜索更好的超参数组合呢

有。先说关键点：**训练一开始的“恶意/怀疑/良性阈值”不一定要固定死**。更好的做法是让模型先输出连续概率或风险分，再用验证集单独选择阈值。也就是：

```text
模型训练：学风险概率 p(malicious)
验证集：选择 良性/疑似/恶意 的切分阈值
测试集：只做最终评估
```

例如：

```text
p >= T_mal      -> 恶意
p <= T_white    -> 良性
中间区域        -> 疑似/人工复核
```

`T_mal` 和 `T_white` 不建议在训练开始时拍脑袋定死。

**比网格搜索更好的方法**

网格搜索可以用，但效率低。更推荐这些方法：

1. 随机搜索
   比网格搜索简单但通常更有效。尤其当超参数很多时，随机搜索更容易碰到好组合。

2. 贝叶斯优化
   适合调学习率、正则化强度、阈值、特征权重约束、类别权重等。它会根据已有实验结果决定下一组更可能好的参数，比盲目网格更省次数。

3. TPE / Optuna
   实操里很好用。Optuna 的 TPE 搜索通常比网格搜索更合适。可以让目标函数直接优化你的业务指标，例如：

```text
最大化：恶意召回率 - 3 * 白样本误报率 - 0.2 * 人工复核比例
```

或设置约束：

```text
白样本误报率 <= 1%
在这个约束下最大化恶意召回率
```

4. Hyperband / ASHA
   如果训练模型比较慢，可以用这个。它会先用少量训练轮次筛掉差的组合，把资源留给表现好的组合。

5. 坐标搜索
   如果你的系统主要是规则阈值，比如 360 权重、移动权重、分身包规则、恶意阈值，可以一次只调一个参数，循环多轮。工程上简单，解释性也强。

6. 贝叶斯优化 + 交叉验证
   如果人工标注数据不多，可以用分组交叉验证。注意要按 `pkgName/signature/应用基础名` 分组，不能随机拆 MD5。

**阈值怎么更稳地调**

建议不要只调一个阈值，而是两个阈值：

```text
T_white：低于它判白
T_mal：高于它判恶意
中间：疑似/人工复核
```

这样可以降低误杀和漏判。

验证集上搜索：

```text
T_white in [0.05, 0.10, 0.15, 0.20, 0.25]
T_mal   in [0.70, 0.75, 0.80, 0.85, 0.90, 0.95]
```

约束：

```text
T_white < T_mal
```

然后选业务最合适的组合。

如果你的目标是少误杀白样本，可以这样选：

```text
白样本误报率 <= 0.5%
在满足条件的组合里，恶意召回率最高
```

如果你的目标是少漏恶意，可以这样选：

```text
恶意召回率 >= 98%
在满足条件的组合里，白样本误报率最低
```

**训练时阈值不合理怎么办**

训练时尽量不要用硬阈值作为标签生成逻辑。应该用可信标签：

```text
人工标注恶意 -> 1
人工标注白 -> 0
武汉确认恶意 -> 1
武汉确认白 -> 0
分身不可安装 -> 单独类别或排除
未确认疑似 -> 不进训练
```

模型输出概率。阈值后置。

如果必须处理三类：

```text
良性 / 疑似 / 恶意
```

也可以训练三分类模型：

```text
softmax -> P(良性), P(疑似), P(恶意)
```

但我建议你先做二分类 + 灰区：

```text
恶意概率低 -> 良性
恶意概率高 -> 恶意
中间 -> 疑似
```

这更稳，也更符合业务复核流程。

**你这个场景推荐的搜索目标**

不要只优化准确率。准确率会被样本比例误导。

建议用业务目标函数：

```text
score =
  2.0 * 恶意召回率
  - 5.0 * 白样本误报率
  - 0.5 * 分身包误判为恶意率
  - 0.2 * 人工复核比例
```

或者使用约束式：

```text
白样本误报率 <= 1%
分身包误判为恶意率 <= 1%
在约束内最大化恶意召回率
```

这个比单纯网格搜索“准确率最高”更合理。

**最终建议**

你的系统可以这样做：

```text
训练集：学习特征权重
验证集：用 Optuna/TPE 搜索阈值、正则化、类别权重、规则开关
测试集：最终评估一次
```

优先推荐：

1. 先固定标签体系，不用初始阈值生成训练标签。
2. 模型输出连续风险概率。
3. 用验证集搜索 `T_white` 和 `T_mal`。
4. 搜索方法用 `Optuna/TPE`，比网格搜索高效。
5. 目标函数按业务成本设计，不要只看准确率。

> 在我的这个项目中，大模型的作用是什么是单纯给出score值还是给出判断依据，如果是给出score值的话，大模型是怎么训练给出的值呢，如果是给出判断依据的话，大模型是怎么训练出越来越精准的判断依据的呢，是给出问答对呢

在你这个项目里，我建议大模型不要作为“最终打分器”，而是作为**研判解释器 + 证据归纳器 + 人工复核助手**。

也就是说：

```text
结构化规则/轻量模型：负责最终 score 和标签
大模型：负责解释为什么、整理证据、提示人工复核点
```

**1. 大模型如果只给 score，可以吗**

可以，但不推荐作为主方案。

原因是 APP 恶意研判依赖很多结构化字段：

- 两个引擎分数
- 病毒名
- 权限
- 签名
- 包名
- 文件大小
- 是否不可安装
- 通联域名/IP
- 是否武汉确认黑/白
- 是否 360 分身包
- 人工标注历史

这些更适合规则模型、逻辑回归、LightGBM、XGBoost 或浅层神经网络。它们可解释、可控、阈值清楚。

如果让大模型直接输出：

```text
score = 93
```

它本质是在根据文本上下文“估计”一个分数。除非你用大量已标注样本做监督微调，否则它的分数稳定性不如结构化模型。

更好的 score 产生方式是：

```text
特征 -> 轻量模型 -> score
```

大模型只解释这个 score：

```text
该样本高风险，因为命中高危权限、仿冒字段、动态通联境外域名；但安装名末尾数字且同基础名多编号，疑似360分身导出包，因此不建议直接按93分判恶意。
```

**2. 如果一定让大模型给 score，怎么训练**

需要监督数据，格式大概是：

```json
{
  "input": {
    "appName": "MOMO陌陌7",
    "pkgName": "...",
    "size": 123456,
    "engine_360": "白样本",
    "engine_cm": "疑似样本",
    "cm_score": 93,
    "is_clone_suffix": true,
    "same_base_name_count": 103,
    "installable": false
  },
  "output": {
    "label": "无效样本/360分身导出包",
    "score": 0,
    "reason": "安装名为稳定应用名加数字后缀，同基础名成组出现，且不可安装，符合360分身导出包特征。"
  }
}
```

训练方式可以是：

- 监督微调 SFT：让模型学习输入字段到输出标签/分数/理由
- 偏好优化：给两个答案，一个好一个差，让模型学会更偏向好的解释
- RAG/规则提示：不改模型参数，把规则和相似案例检索出来放进 prompt

但直接训练大模型给 score 有几个问题：

- 需要大量高质量样本
- score 一致性不好控制
- 解释可能看起来合理但事实不稳
- 后续规则变化时要重新整理训练数据
- 业务上难追责

所以不建议作为第一优先级。

**3. 大模型更适合给判断依据**

这更符合你的项目。

它可以做这些事：

1. 把结构化字段转成研判理由
   例如把权限、通联、病毒名、分数、武汉标签、人工历史整理成一段可读说明。

2. 发现冲突点
   例如：
   - 360 判白，移动判 93
   - 武汉白样本，但移动高分
   - appName 像分身包，size 又明显异常
   - 病毒名和行为证据不一致

3. 生成复核建议
   例如：
   - 建议人工复核安装可用性
   - 建议比对真实应用大小
   - 建议检查同签名样本
   - 建议检查同基础名分身批次

4. 给出分类依据模板
   统一输出：
   - 结论
   - 证据
   - 冲突点
   - 风险等级
   - 建议动作

**4. 大模型怎么让判断依据越来越准**

有三种路线，从简单到复杂：

**路线 A：不训练模型，做规则 + 案例检索**

这是最推荐的起步方式。

你维护一个规则库和案例库：

```text
规则：安装名为稳定应用名+数字后缀，同基础名成组出现，且不可安装，判为360分身导出包。
案例：MOMO陌陌5/6/7，移动93分，但人工确认为分身导出包。
```

大模型每次研判时检索相似案例和规则，再生成依据。

优点：

- 不需要微调
- 更新规则很快
- 可解释
- 风险低

**路线 B：用问答对/样例做 SFT**

是的，可以做问答对，但最好不是普通聊天问答，而是“结构化输入 -> 标准化研判输出”。

训练样本可以这样：

```json
{
  "instruction": "根据APP检测字段给出研判依据，不要臆测，必须引用输入证据。",
  "input": "appName=MOMO陌陌7; cm_score=93; 360=白样本; same_base_name_count=103; installable=false; size_ratio=0.08",
  "output": "结论：360分身导出包/无效样本。依据：安装名为稳定应用名MOMO陌陌加数字后缀，同基础名出现103条；样本不可安装，且文件大小明显小于真实应用；移动侧93分仅作为疑似风险，不作为恶意定性依据。建议：不计入普通恶意样本，单独归档。"
}
```

这样训练出来的是“解释风格和证据引用能力”，不是让模型凭空判断。

**路线 C：偏好优化**

你可以收集人工对模型输出的评价：

```text
A解释：引用了字段，结论克制，指出冲突点
B解释：只说高风险，没有证据
```

让模型学习偏好 A。

这适合后期提高表达质量和一致性。

**5. 问答对应该怎么设计**

不要设计成：

```text
问：这个APP恶意吗？
答：恶意。
```

这样价值很低。

应该设计成：

```text
输入：完整结构化字段
输出：标准研判报告
```

建议输出格式固定：

```text
结论：
风险等级：
主要证据：
冲突点：
是否命中已知规则：
建议动作：
置信度：
```

例如：

```text
结论：疑似360分身导出包，不按恶意APP入库
风险等级：低风险/无效样本
主要证据：安装名为MOMO陌陌7，基础名MOMO陌陌下存在多个数字后缀样本；移动API给93分，但360判白；样本不可安装且大小异常。
冲突点：移动API高分与360白样本冲突。
命中规则：稳定应用名+数字后缀成组出现。
建议动作：归入分身导出包池，排除出恶意训练集。
置信度：高
```

**6. 最推荐的架构**

你的项目可以这样分工：

```text
数据层：
人工标注、武汉黑白样本、两个引擎输出、APP静态/动态字段

规则层：
分身包规则、武汉黑白优先级、强冲突规则、白名单规则

模型层：
轻量模型学习score和风险概率

大模型层：
读取字段 + 规则命中 + 相似案例
输出研判依据、冲突说明、复核建议
```

最终：

```text
final_score：由规则/轻量模型给
final_label：由规则/轻量模型给
reason：由大模型生成
```

这比让大模型单独给 score 更稳。

**一句话总结**

大模型在你的项目里最好不是“判官”，而是“会写研判依据的分析员”。
score 和标签由可控的规则/轻量模型产生；大模型负责把证据、冲突点、规则命中和复核建议讲清楚。训练大模型时可以用问答对，但应是“结构化样本字段 -> 标准研判报告”的监督样本，而不是简单“这个是不是恶意”的问答。

也就是：

**一、你应该在哪里精修 prompt**

最值得精修的是这几类 prompt。

**1. 研判依据生成 prompt**

输入：

```text
APP基础字段
两个引擎结果
武汉接口黑白标签
人工标注历史
规则命中结果
```

输出：

```text

风险等级
主要证据
冲突点
命中规则
建议动作

```

这个 prompt 决定大模型是否能“按证据说话”，不要乱猜。

例如：

```text
你是APP安全研判助手。只能根据输入字段和规则库生成结论，不得补充输入中没有的事实。
如果证据冲突，必须单独列出冲突点。

输出必须包含：结论、风险等级、主要证据、冲突点、建议动作。
```

**2. 冲突样本复核 prompt**

专门用于两个引擎不一致：

```text
360判白，移动判疑似/恶意
360判恶意，移动判白/疑似
武汉接口与两个引擎冲突
```

这个 prompt 要强调“冲突来源”和“为什么不能直接按高分判恶意”。

**3. 分身包/不可安装样本 prompt**

这是你当前最需要固化的规则：

```text
安装名为稳定应用名+数字后缀
同一基础名出现多个编号
导出APK不可安装
大小与真实应用差距大
移动API按风险等级给93分
```

prompt 里要明确：

```text
此类样本应单独归为“360分身导出包/无效样本”，不要作为普通恶意APP训练样本。
```

**4. 人工复核建议 prompt**

用于输出：

```text
建议查安装可用性
建议查真实应用大小
建议查同签名/同包名样本
建议查同基础名批次
建议人工确认
```

这个适合辅助人工标注。

**二、怎么判断 prompt 是好的**

不要靠主观感觉，要做一个小型 prompt 测试集。

从你已有数据里挑 50 到 200 条代表样本：

- 武汉确认恶意
- 武汉确认白样本
- 人工标注强冲突
- 人工标注弱冲突
- 360 分身导出包
- 两个引擎一致恶意
- 两个引擎一致白
- 边界样本，比如 score=89/93/97/100

然后每次改 prompt，都跑同一批样本，看输出是否满足标准。

好的 prompt 至少满足：

1. 结论稳定
   同样输入多次运行，结论基本一致。

2. 不越权判断
   没有输入证据时，不编造权限、域名、病毒名、安装状态。

3. 能处理冲突
   会明确说“360判白但移动给93分”，而不是只看高分。

4. 能遵守业务规则
   命中 360 分身规则时，不直接判恶意。

5. 输出结构固定
   方便入库和后续统计。

6. 证据可追溯
   每条理由都能对应输入字段。

7. 错误可控
   不确定时输出“需人工复核”，而不是硬判。

你可以给 prompt 做评分表：

```text
结论是否正确：0/1
是否引用关键证据：0/1
是否编造事实：0/1
是否列出冲突点：0/1
是否遵守分身规则：0/1
输出格式是否合规：0/1
```

一个 prompt 是否好，不看它写得多漂亮，而看它在固定测试集上的合规率。

**三、什么是模型推理**

模型推理就是：

```text
给模型输入 prompt 和数据，模型输出结果
```

训练是改模型参数。
推理是不改模型参数，只让模型根据当前输入生成答案。

例如：

```text
输入：
appName=MOMO陌陌7
cm_score=93
360=白样本
命中分身规则=是

推理输出：
结论：360分身导出包/无效样本
依据：……
```

这就是一次推理。

**四、模型推理的参数是什么**

常见推理参数有这些。

**1. temperature**

控制随机性。

```text
temperature 低：输出稳定、保守
temperature 高：输出发散、多样
```

你的研判任务建议：

```text
temperature = 0 或 0.1
```

不要用高温度。安全研判需要稳定，不需要创意。

**2. top_p**

控制采样范围。

```text
top_p 越低，模型只从高概率词里选
top_p 越高，输出更发散
```

你的任务建议：

```text
top_p = 0.1 到 0.3
```

或者如果 temperature 已经很低，top_p 保持默认也可以。

**3. max_tokens**

控制最大输出长度。

建议固定输出结构，长度不要太大，例如：

```text
max_tokens = 500 到 1000
```

如果要输出完整研判报告，可以更高。

**4. stop**

指定遇到什么字符串停止输出。

比如你批量处理时，可以设置：

```text
stop = ["\n\nEND"]
```

不是必须。

**5. response_format / JSON schema**

如果你要入库，强烈建议让模型输出 JSON。

例如：

```json
{
  "conclusion": "",
  "risk_level": "",
  "evidence": [],
  "conflicts": [],
  "matched_rules": [],
  "recommendation": "",
  "confidence": ""
}
```

这比自然语言更容易质检。

**6. seed**

有些模型支持 seed，用于提高可复现性。

```text
seed 固定 -> 同样输入更容易得到相同输出
```

但不是所有模型都支持。

**7. presence_penalty / frequency_penalty**

控制重复和话题发散。你的任务一般不需要调，默认即可。

**五、你的项目推荐推理配置**

建议：

```text
temperature = 0 或 0.1
top_p = 0.2 或默认
max_tokens = 800
response_format = JSON
```

并且 prompt 明确：

```text
只能根据输入字段判断。
不得编造证据。
如果证据不足，输出“需人工复核”。
命中分身规则时，不得按93分直接判恶意。
输出 JSON。
```

**六、最实用的 prompt 模板**

```text

1. 只能使用输入中出现的事实，不得编造权限、域名、安装状态、病毒名或历史结论。
2. final_label 和 final_score 已由规则/模型给出，你不得擅自修改，只能解释。
3. 如果两个引擎、武汉标签、人工标签之间存在冲突，必须列入 conflicts。
4. 如果命中“360分身导出包”规则，必须说明：移动API高分不能单独作为恶意定性依据。

}
```

**1. 大模型微调的目的**

大模型微调可以有两个目标，但在你的项目里要分开看。

第一类：让它“说得更标准”。
这是最适合大模型微调的方向。也就是让模型输出更规范的研判报告：

```text
结论：
风险等级：
主要证据：
冲突点：
命中规则：
建议动作：
置信度：
```

这种微调主要学习的是：

- 输出格式
- 业务术语
- 证据组织方式
- 不乱编字段
- 遇到冲突样本时怎么表达
- 遇到 360 分身包时怎么说明

第二类：让它“判断得更标准”。
也可以做，但风险更高。因为 APP 恶意判断依赖结构化字段、规则、历史标签、引擎分数。大模型如果直接判断，容易出现不稳定、不可解释、受 prompt 影响大等问题。

所以我建议：

```text
大模型微调优先用于“解释标准化”
最终判断优先由规则/轻量模型/神经网络给出
```

如果你一定要让 LoRA 让模型判断更标准，需要这样做：

```text
输入：完整结构化字段 + 规则命中结果 + 两个引擎输出 + 武汉标签 + 人工历史
输出：标准 label + reason
```

```text

```

```json

  "input": {
    "appName": "MOMO陌陌7",
    "engine_360_label": "白样本",
    "engine_cm_label": "疑似样本",
    "engine_cm_score": 93,

```

LoRA 要让判断更标准，关键不是 LoRA 本身，而是训练数据要标准：

```text
减少重新微调成本
```

你现在这类项目，优先级建议是：

```text
第一优先级：规则体系 + 数据集划分 + 轻量模型学权重
第二优先级：Prompt/RAG 生成标准研判依据
第三优先级：LoRA 微调大模型，让输出格式和判断口径更稳定
```

**最关键结论**

大模型 LoRA 的主要价值是让它：

```text
说得标准
引用证据标准
解释冲突标准
复核建议标准
```

如果要让它“判断更标准”，必须给它大量高质量的结构化训练样本，并且标签体系已经稳定。但即便如此，我仍建议最终 score 由轻量模型/神经网络给，大模型负责解释。

模型甲、乙现在的平均分、最强分、最弱分和权重是人为规定的。后续可以把这些权重改成可学习参数，用人工标注和武汉黑白样本训练出来。

> 1，WEC的初始权重能不做超参数吗，做参数计算梯度和loss来选择2，有哪些特征权重可以训练就是输入的60+字段可以把每个当作特征权重再计算吗，我可以将大模型当作一个网络来训练这些参数吗3，什么是模型甲和乙，难道本地部署的大模型就只是输出证据块吗

可以。你现在问到的是核心设计问题：**哪些东西应该作为可学习参数，哪些东西不应该交给大模型直接学。**

**1. WEC 初始权重能不能不做超参数，而作为参数用梯度学习？**

可以。

如果 WEC 指的是类似：

```text
Weighted Evidence Combination
加权证据融合
```

比如：

```text
final_score =
  w_static * static_score
+ w_intel * intel_score
+ w_fake * fake_score
+ w_business * business_score
+ w_360 * score_360
+ w_cm * score_cm
```

这里的 `w_static, w_intel, w_fake...` 完全可以不当超参数，而是当**模型参数**。

训练方式：

```text
输入特征 x
可学习权重 w
输出恶意概率 p
用人工/武汉标签计算 loss
反向传播更新 w
```

例如：

```text
logit = b + w1*x1 + w2*x2 + w3*x3 + ...
p = sigmoid(logit)
loss = binary_cross_entropy(p, label)
```

这就是逻辑回归，本质上就是一个最简单的神经网络。

但注意：**阈值仍然建议放到验证集调。**

也就是说：

```text
训练集：学习 WEC 权重
验证集：选择恶意阈值、白样本阈值、人工复核区间
测试集：最终评估
```

不要把所有东西都放进训练集里学，否则容易过拟合。

**2. 60+ 字段能不能每个都当特征训练权重？**

原则上可以，但不要直接把“原始字段”全部粗暴丢进去。

你的 60+ 字段大概有几类：

```text
数值字段：score、size、url_count、权限数量
布尔字段：fakeApp、genuine、isIllegal、malicious、violation
类别字段：fileType、riskLevel、fraudType、病毒类型
文本字段：appName、pkgName、virusName、domain、permissions JSON
JSON/列表字段：permissions、plugins、dynamicNets、ltUrls
```

不同字段处理方式不同。

可以直接训练权重的：

```text
score_360
score_cm
size_mb
permission_count
high_risk_permission_count
dynamic_url_count
static_url_count
foreign_domain_count
ip_count
domain_count
is_fake_app
is_genuine
is_illegal
has_packer
is_clone_suffix_group
is_uninstallable
size_abnormal
wuhan_malicious
wuhan_white
```

需要编码后再训练的：

```text
fraudType
fraudCategory
codeSafeRiskLevel
fileType
riskEvaluateResult
virusName 家族
operator/country
sdkType
```

需要先抽特征的：

```text
permissions JSON -> 高危权限数量、短信权限、悬浮窗权限、安装权限
plugins JSON -> 高危SDK数量、广告SDK数量、统计SDK数量
ltUrls/dynamicNets -> 动态通联数量、境外域名数量、主控URL命中
appName -> 是否末尾数字、是否分身组、是否色情/贷款/刷单关键词
pkgName -> 是否随机包名、是否仿冒知名包名、是否无意义字符串
signature -> 是否异常、是否同签名聚类
```

不建议直接让每个原始字符串字段都有一个权重。比如：

```text
appName="MOMO陌陌7"
domain="xxx.com"
permissions="[...巨大JSON...]"
```

这些不能直接当数值权重。要先变成结构化特征。

更合理的是：

```text
60+ 原始字段
-> 特征工程
-> 100~500 个结构化特征
-> 逻辑回归 / LightGBM / 小神经网络
-> final_score
```

**能不能把大模型当作一个网络来训练这些参数？**

理论上可以，但不建议。

大模型当然也是神经网络，可以微调 LoRA。但它不适合专门学习这种表格字段权重。原因：

1. 成本高
   为了学几十个结构化权重，微调大模型太重。

2. 可解释性差
   你很难知道 `score_cm=93`、`is_clone_suffix=1` 到底在大模型内部产生了多大权重。

3. 稳定性不如轻量模型
   同样字段，大模型输出可能受 prompt、上下文顺序、采样参数影响。

4. 表格结构化任务不是大模型强项
   逻辑回归、LightGBM、小 MLP 更合适。

你可以这样分工：

```text
轻量模型/神经网络：训练字段权重，输出 final_score
大模型：读取 final_score + 证据特征，输出标准研判依据
```

如果你非要让“大模型参与判断”，更建议让它输出一个辅助特征，而不是最终裁决：

```text
llm_risk_opinion = 0/1/2
llm_confidence = 0~1
llm_matched_rules = [...]
```

然后把这些作为特征交给轻量模型融合。

**3. 什么是模型甲和乙？本地大模型是不是只输出证据块？**

按你现在项目里的设计，模型甲和模型乙不是两个真正训练好的独立模型，更像是两个“角色化研判视角”。

模型甲：

```text
保守复核模型
更重视证据是否充分
防止单一高风险信号导致误杀
```

模型乙：

```text
风险优先模型
更重视高危 IOC、仿冒、涉诈家族、高危权限
防止漏掉恶意样本
```

你当前代码里，它们的初始分数来自人工公式：

```text
模型甲 = 平均证据分 * 0.86 + 最弱证据分 * 0.14
模型乙 = 平均证据分 * 0.78 + 最强证据分 * 0.22
```

这不是训练出来的，是人为设定的。

本地部署的大模型现在主要作用是：

```text
读取四个证据块
按“保守视角”或“风险优先视角”
输出 JSON 研判意见、理由、可能的 score/verdict
```

所以它不只是输出证据块。证据块是四个智能体先生成的，大模型甲/乙是拿证据块做二次研判。

流程是：

```text
四个智能体 -> 生成证据块和分数
模型甲 -> 保守复核这些证据
模型乙 -> 风险优先复核这些证据
仲裁器 Engine C -> 融合甲乙结果和最强证据
```

但现在的问题是：模型甲乙和仲裁器的权重仍然是人工规则，不是真正学出来的。

更成熟的版本应该是：

```text
四个智能体输出结构化特征
-> WEC/轻量模型学习权重
-> 输出 final_score/final_label
-> 大模型甲乙只负责从不同视角解释和质检
```

也可以保留甲乙，但让它们不直接定分：

```text
模型甲输出：是否证据不足、是否建议降级、误报风险点
模型乙输出：是否存在高危信号、是否建议升级、漏报风险点
轻量模型融合这些结构化结果
```

**建议你的最终架构**

```text
第一层：字段特征化
60+字段 -> 数值/布尔/类别/文本特征

第二层：四个智能体
静态分析、情报溯源、仿冒、业务标签
输出 evidence_score + evidence_flags

第三层：可学习 WEC
用人工标注和武汉黑白样本训练权重
输出 final_score

第四层：阈值策略
验证集选择：
p <= T_white -> 白
p >= T_mal -> 恶意
中间 -> 疑似/人工复核

第五层：大模型
根据 final_score、证据、冲突点生成标准研判依据
```

一句话：

**WEC 权重可以作为参数用梯度和 loss 学出来；60+字段可以训练，但要先特征化；大模型不要拿来学这些权重，最好让轻量模型负责判断，大模型负责解释、复核和标准化输出。**

> 1，optimizer,weight decay,warmup ratio,lora rank,lora alpha,dropout,max sequence length是超参数吗，可以训练这些得到什么，2，训练集是训练什么的呢，训练怎么打分的吗，还是训练输出证据快，对每个模块训练集训练的目的是什么说清楚，详细解析

**1. 这些是不是超参数**

是，下面这些基本都属于**训练超参数**或**微调配置超参数**：

```text
optimizer
weight decay
warmup ratio
LoRA rank
LoRA alpha
dropout
max sequence length
learning rate
batch size
epoch
gradient accumulation
```

它们一般不是模型在训练中自动学出来的参数，而是你在训练前设定，用验证集或实验搜索选择。

逐个解释：

| 名称 | 是什么 | 影响什么 |
|---|---|---|
| `optimizer` | 优化器，例如 AdamW、SGD | 决定模型参数怎么更新 |
| `weight decay` | 权重衰减，正则化 | 防止过拟合 |
| `warmup ratio` | 学习率预热比例 | 训练初期更稳定 |
| `LoRA rank` | LoRA 低秩矩阵维度 | 决定 LoRA 可学习容量 |
| `LoRA alpha` | LoRA 缩放系数 | 控制 LoRA 更新强度 |
| `dropout` | 随机丢弃部分神经元 | 防止过拟合 |
| `max sequence length` | 最大输入长度 | 决定一次能放多少字段/证据 |
| `learning rate` | 学习率 | 控制参数更新步长 |
| `batch size` | 批大小 | 影响稳定性、显存和收敛 |
| `epoch` | 训练轮数 | 影响是否欠拟合/过拟合 |

这些通常通过验证集、随机搜索、贝叶斯优化、经验配置来选，而不是直接反向传播学出来。

**能不能训练这些超参数？**

严格说，普通训练过程训练的是：

```text
模型权重参数
LoRA 增量参数
轻量模型权重
```

不是训练：

```text
optimizer
dropout
LoRA rank
max sequence length
```

有些高级方法可以做“超参数优化”或“元学习”，比如自动搜索 `learning rate`、`weight decay`、`rank`，但这不是普通反向传播训练模型参数，而是外层搜索过程。

例如：

```text
内层训练：固定 learning rate，训练模型权重
外层验证：看验证集效果，换 learning rate 再训练
```

这叫超参数搜索，不是模型自己直接学出来。

**训练这些超参数得到什么？**

更准确地说，不是“训练它们”，而是“选择它们”。

选择好这些超参数，会得到：

- 更稳定的训练过程
- 更低的验证集 loss
- 更高的验证集准确率/召回率
- 更少过拟合
- 更好的格式遵循
- 更好的泛化能力

比如：

```text
LoRA rank 太小 -> 学不动业务风格
LoRA rank 太大 -> 容易过拟合、显存更高
weight decay 太小 -> 过拟合
weight decay 太大 -> 学不进去
max sequence length 太短 -> 字段被截断，判断依据缺失
dropout 太高 -> 输出质量下降
```

**2. 训练集到底是训练什么**

你这个项目里不要只说“训练集训练模型”，要分模块说。

你的系统至少有四类东西：

```text
A. 四个智能体的规则/特征提取模块
B. WEC/轻量评分模型
C. 阈值决策层
D. 大模型/LoRA 解释层
```

每一层“训练”的目的不一样。

---

**A. 四个智能体训练什么**

四个智能体是：

```text
静态分析智能体
情报溯源智能体
仿冒研判智能体
业务标签智能体
```

如果它们现在是规则写死的，那么训练集不直接训练它们，只用来验证规则是否合理。

例如：

```text
高危权限 +0.15
签名异常 +0.25
境外动态通联 +0.20
```

这些如果是人工写死，就不是训练出来的。

但你可以把它们升级成可学习模块。

例如静态分析智能体：

输入特征：

```text
signature_abnormal
high_risk_permission_count
has_packer
permission_sms
permission_overlay
permission_install
```

输出：

```text
static_risk_score
```

训练目标：

```text
让 static_risk_score 更接近人工/武汉标签中体现出的静态风险贡献
```

但现实中你通常没有“静态智能体单独标签”，只有最终恶意/白标签。所以更常见做法是：

```text
四个智能体只负责抽取结构化特征
最终由 WEC/轻量模型统一学习权重
```

也就是说，四个智能体的主要训练目标不是“单独学会最终判断”，而是：

```text
把原始60+字段变成稳定、可用、可解释的证据特征
```

比如：

```text
原始 permissions JSON
-> high_risk_permission_count=5
-> has_sms_permission=1
-> has_overlay_permission=1
```

---

**B. WEC/轻量评分模型训练什么**

这是最应该用训练集训练的部分。

WEC 可以理解为：

```text
Weighted Evidence Combination
加权证据融合模型
```

输入：

```text
static_score
threat_intel_score
impersonation_score
business_label_score
engine_360_score
engine_cm_score
wuhan_malicious
wuhan_white
is_clone_suffix_group
is_uninstallable
size_abnormal
high_risk_permission_count
foreign_domain_count
dynamic_url_count
```

输出：

```text
恶意概率 p
```

训练集训练的是这些参数：

```text
w_static
w_intel
w_impersonation
w_business
w_360
w_cm
w_wuhan_malicious
w_wuhan_white
w_clone_suffix
w_uninstallable
...
bias
```

公式类似：

```text
logit =
  b
  + w1 * static_score
  + w2 * threat_intel_score
  + w3 * impersonation_score
  + w4 * business_label_score
  + w5 * engine_360_score
  + w6 * engine_cm_score
  + w7 * is_clone_suffix_group
  + w8 * is_uninstallable

p = sigmoid(logit)
```

训练怎么打分？

训练时模型先输出 `p`，然后和真实标签比较。

例如：

```text
人工标注恶意 -> y=1
武汉确认恶意 -> y=1
人工标注白 -> y=0
武汉确认白 -> y=0
360分身不可安装 -> 单独类，或不进入二分类训练
```

损失函数：

```text
loss = binary_cross_entropy(p, y)
```

如果预测错，loss 大；预测对，loss 小。
优化器根据 loss 的梯度更新权重。

所以 WEC 训练的目的非常明确：

```text
训练最终风险分数怎么计算
训练不同证据应该占多大权重
训练哪些特征应该加风险，哪些特征应该降风险
```

---

**C. 阈值层训练什么**

阈值层一般不叫训练，叫**验证集调参**。

WEC 输出的是概率：

```text
p = 0.83
```

但业务要的是：

```text
白样本 / 疑似 / 恶意 / 人工复核
```

所以需要阈值：

```text
p <= T_white -> 白样本
T_white < p < T_mal -> 疑似/人工复核
p >= T_mal -> 恶意
```

`T_white` 和 `T_mal` 不建议训练集学，而是验证集选择。

验证集调的是：

```text
白样本误报率
恶意召回率
人工复核比例
分身包误判率
```

例如业务要求：

```text
白样本误报率 <= 1%
在这个约束下最大化恶意召回率
```

那么就在验证集上搜索最合适的：

```text
T_white
T_mal
```

阈值层的目的：

```text
把连续风险概率变成符合业务成本的决策
```

---

**D. 大模型/LoRA 训练什么**

大模型微调和 WEC 完全不是一回事。

大模型 LoRA 的训练输入一般是：

```text
结构化字段 + WEC final_score + 规则命中 + 冲突信息
```

输出是：

```text
标准研判报告
```

例如：

```json
{
  "conclusion": "360分身导出包/无效样本",
  "risk_level": "低",
  "evidence": [
    "安装名为稳定应用名+数字后缀",
    "同一基础名成组出现",
    "样本不可安装",
    "移动API给93分但不能单独作为恶意依据"
  ],
  "conflicts": [
    "360判白，移动判疑似"
  ],
  "recommendation": "不计入普通恶意样本，单独归档"
}
```

LoRA 训练的参数是：

```text
大模型某些层上的低秩增量矩阵
```

训练目的：

```text
让模型输出格式更稳定
让模型使用你的业务术语
让模型不乱编证据
让模型知道冲突样本怎么写
让模型知道360分身包怎么解释
让模型按固定JSON输出
```

如果你让 LoRA 同时输出 label，也可以训练它判断：

```text
输入字段 -> 输出 label + reason
```

但我不建议让它成为最终判断来源。更稳的是：

```text
WEC/轻量模型给 label 和 score
LoRA 大模型解释 label 和 score
```

---

**各模块训练目的总结**

| 模块 | 是否用训练集 | 训练什么 | 输出什么 |
|---|---:|---|---|
| 特征工程/四个智能体 | 通常不直接训练 | 把60+字段变成证据特征 | evidence flags / evidence score |
| WEC/轻量模型 | 是 | 学习证据权重 | final_score / malicious probability |
| 阈值层 | 用验证集，不用训练集 | 选择白/疑似/恶意阈值 | final_label |
| 大模型 LoRA | 可选 | 学输出格式、术语、解释方式 | 标准研判依据 |
| 大模型直接判断 | 不优先 | 学 label + reason 映射 | label/reason，但风险更高 |

---

第一步，构建统一标签：

```text
武汉恶意 -> 1
武汉白 -> 0
分身不可安装 -> 单独类别或排除
未标注冲突 -> 不进训练
```

第二步，做特征表：

```text
md5
static_score
intel_score
impersonation_score
business_score
engine_360_score
engine_cm_score
is_clone_suffix_group
```

**2. 反驳 prompt 怎么写，是找错加反驳吗**

是的，本质是让模型从另一个角度做**质检、找漏洞、指出过度判断或漏判风险**，但不要让它胡乱争辩。

你可以设计两个反驳角色。

模型甲：保守反驳，防误杀。

```text

1. 只能基于输入字段反驳，不得编造事实。
2. 优先寻找误报风险。
3. 如果发现判断过度，指出应该降级或人工复核的原因。
4. 如果证据充分，也要说明“未发现明显误报风险”。
5. 输出 JSON。
```

输出：


模型乙：风险反驳，防漏报。

```text
你是风险优先复核模型。请审查当前良性或低风险判断是否低估了恶意风险，重点检查高危权限、IOC、仿冒、涉诈家族、动态通联、武汉黑样本证据。
```


反驳 prompt 不是为了“吵架”，而是为了覆盖两种错误：

```text

```

**3. 每个智能体的 confidence 怎么确定**

不要让 confidence 只是模型随口说。最好用可计算规则。

每个智能体可以有两个分：

```text
risk_score：风险强度
confidence：这个智能体对自己结论的可靠程度
```

风险高不等于置信度高。

例如：

```text
风险分高：发现了高危权限
置信度低：缺少签名、包名、安装状态等关键字段
```

每个智能体的 confidence 可以由这几部分组成：

```text
confidence =
  字段完整度 * 0.4
+ 证据强度 * 0.4
+ 证据一致性 * 0.2
```

举例。

静态分析智能体：

```text
字段完整度：
是否有 permissions
是否有 signature
是否有 packer
是否有 size
是否有 pkgName

证据强度：
高危权限数量
签名异常
加固/混淆
大小异常

证据一致性：
多个静态信号是否同向
```

情报溯源智能体：

```text
字段完整度：
是否有 dynamicNets
是否有 ltUrls
是否有 domain/ip
是否有 whois/icp/asn

证据强度：
IOC命中数量
主控/下载地址命中
境外/匿名/CDN/高危域名

证据一致性：
动态通联、静态通联、域名情报是否一致
```

仿冒智能体：

```text
字段完整度：
是否有 appName
pkgName
iconMd5
genuine/fakeApp
brand_similarity

证据强度：
fakeApp=true
品牌相似度高
包名相似但签名不同
图标相似

证据一致性：
名称、图标、包名是否共同指向仿冒
```

业务标签智能体：

```text
字段完整度：
是否有 virusName
fraudType
fraudCategory
antiFraudLabel
武汉标签
人工标签

证据强度：
武汉确认黑
人工确认恶意
病毒家族明确
涉诈类别明确

证据一致性：
多个来源标签是否一致
```

简单公式：

```text
confidence = min(1.0,
    0.2
  + 0.3 * field_coverage
  + 0.3 * evidence_strength
  + 0.2 * source_agreement
)
```

如果字段缺失严重，就算 risk_score 高，也要降低 confidence。

**4. 模型甲和乙的置信度如何确定**

模型甲乙的 confidence 不建议让大模型自由生成。可以让它输出自评，但最终最好用程序校准。

模型甲是保守复核，置信度可以看：

```text
误报风险证据是否充分
白样本/分身包/不可安装/武汉白标签是否存在
反驳点数量和强度
输入字段完整度
```

模型乙是风险优先，置信度可以看：

```text
恶意证据是否充分
武汉黑标签/人工恶意/IOC/高危权限/仿冒/涉诈家族是否存在
反驳点数量和强度
输入字段完整度
```

可以这样计算：

```text
model_a_confidence =
  0.4 * conservative_evidence_strength
+ 0.3 * relevant_field_coverage
+ 0.2 * conflict_strength
+ 0.1 * agreement_with_known_labels
```

```text
model_b_confidence =
  0.4 * malicious_evidence_strength
+ 0.3 * relevant_field_coverage
+ 0.2 * high_risk_signal_count
+ 0.1 * agreement_with_known_labels
```

例如命中这些时，模型甲置信度升高：

```text
武汉白样本
人工白样本
360白样本
分身包规则
不可安装
大小异常
移动93分但缺少真实恶意证据
```

命中这些时，模型乙置信度升高：

```text
武汉恶意样本
人工恶意样本
两个引擎均恶意
明确病毒家族
C2/主控地址
高危权限组合
仿冒金融/支付/贷款
动态通联异常
```

最后还可以做校准：

```text
如果模型甲建议降级，但历史验证集中这类建议正确率只有70%，那甲的置信度上限设为0.7
如果模型乙建议升级，在验证集中正确率90%，那乙的置信度可更高
```

这叫置信度校准，比让大模型自己说“我有 0.9 置信度”可靠得多。

**推荐实现方式**

```text
四个智能体：
risk_score 程序计算
confidence 程序计算

模型甲乙：
大模型输出 challenge_points 和 suggested_adjustment
程序根据证据覆盖、规则命中、历史校准计算 confidence

最终仲裁：
WEC/轻量模型融合 risk_score、confidence、甲乙建议
```

一句话总结：

1. 大模型训练用“结构化字段 -> 标签 + 标准研判依据”，不是普通问答，也不是只有标签。
2. 反驳 prompt 是找错和质检，甲防误杀，乙防漏报。
3. 每个智能体 confidence 应由字段完整度、证据强度、证据一致性计算。
4. 模型甲乙 confidence 最好由程序根据反驳证据和验证集校准，不要完全相信大模型自报置信度。

简单说：你在这个 `工作` 文件夹里用了 Git，Git 不只是保存“当前文件”，还会保存很多历史版本。`.git/objects` 里放的就是这些历史数据。

它里面可能包括：

- 你提交过的文件内容
- 每次 commit 的快照信息
- 分支、标签相关对象
- 被删除但仍在 Git 历史里的大文件
- Git 打包后的对象文件，例如 `.pack`
- 临时/悬空对象，例如曾经 `git add` 过但后来没提交的大文件

所以它不是普通缓存，不能直接删：

```text
不要手动删除 .git/objects
```

否则 Git 仓库可能损坏，`git status`、`git log`、恢复历史都会出问题。

你这里 `.git/objects` 有 **175 GB**，非常不正常。大概率是以下情况之一：

1. 曾经把大数据库、模型文件、Excel、大压缩包、打包产物提交进 Git
   比如 `.db`、`.xlsx`、`.pt`、`.bin`、`.exe`、`release/`、`.venv/`。

2. 曾经 `git add` 过大文件，后来又删掉了
   即使当前目录没了，Git 对象里可能还留着。

3. 多次打包生成物进入了 Git 历史
   比如 `dist/`、`release/`、`.build_*`。

4. Git 没有做垃圾回收
   一些悬空对象还没被清掉。

通俗比喻一下：

```text
工作目录 = 你现在桌面上看到的文件
.git/objects = Git 的历史仓库和回收库
```

你现在真正大的是“历史仓库”，不是当前普通文件。



很多正常 APP 也会申请：

```text

存储
电话状态
运行应用列表
截图相关能力
保活相关能力
```

如果只因为这些能力就给 93，疑似样本会非常多。

这会造成：

```text
CM 疑似样本膨胀
360 白 vs CM 疑似 大量出现
```

我逐条拆开。

**1. 规则变化时，旧模型容易被高分误导**

比如 `MOMO陌陌5/6/7` 这种样本。

从 CM 的角度看，它可能发现：

```text
有敏感权限
有获取手机信息风险
安装名像真实APP
score = 93
类型 = 研判疑似样本
```

如果旧模型只学到：

```text
CM score 高 -> 风险高
```

那它很可能也会跟着判：

```text
疑似恶意 / 高风险
```

但你后来人工发现，这类样本很多是：

```text
360 分身应用导出的 APK
安装名后面带数字
导出的 APK 可能不可安装
大小和真实 APP 差距很大
并不等同于真实恶意 APP
```

这就叫“规则变化”。

以前没有“分身导出包”这个规则时，模型只会按高分风险处理。
现在你新增了业务规则：

```text
稳定应用名 + 数字后缀
同基础名批量出现
不可安装
大小异常
-> 优先判为分身导出包/无效样本
```

所以，旧模型容易被 CM 的 93 分误导；新系统会额外检查它是不是分身包。

一句话：

```text
旧模型只看分数，新系统还看这个高分是不是由特殊样本形态造成的。
```

---

**2. 单一模型很难区分真实恶意 APP 和不可安装/分身导出/无效样本**

真实恶意 APP 是：

```text
可以安装或运行
有明确恶意行为
例如诈骗、色情诱导、博彩、恶意广告、窃取信息、主控通信
```

不可安装/分身导出/无效样本是：

```text
可能只是从分身环境导出的包
结构不完整
无法正常安装
大小异常
名字像真实APP加数字
不代表真实用户会安装运行的恶意APP
```

但是它们在某些特征上可能很像。

例如两者都可能有：

```text
敏感权限
读取设备信息
奇怪包名
非官方签名
应用名异常
```

如果只有一个模型，它看到这些特征，可能只会输出：

```text
风险高
```

但它不知道：

```text
这个风险是来自真实恶意行为？
还是来自分身导出导致的异常？
还是来自样本不可安装？
```

所以需要加中间判断：

```text
先判断样本是否有效
再判断是否分身导出包
再判断是否真实恶意
```

也就是：

```text
样本有效性判断
-> 分身包/无效包识别
-> 恶意风险判断
```

如果不做这一步，训练集也会被污染。
你可能会把大量“无效分身包”当成恶意样本训练进去，模型以后看到正常 APP 分身也会误杀。

一句话：

```text
单一黑白模型只能回答“像不像风险”，但不能回答“这个样本是不是一个有效的真实恶意APP”。
```

---

**3. 人工复核经验没有很好沉淀成可追溯证据**

这个意思是：人工看过样本以后，不能只在脑子里记住“这个不是恶意”，而要把判断理由结构化保存下来。

比如人工复核时发现：

```text
MOMO陌陌5、MOMO陌陌6、MOMO陌陌7
是 360 分身导出包
不可安装
大小异常
所以不按普通恶意APP入库
```

如果只是口头说：

```text
这批不用管
```

那下次系统遇到：

```text
QQ1
快手1
支付宝1
蜂鸟众包1
```

它还是不知道怎么处理。

这就叫人工经验没有沉淀。

正确做法是把人工经验保存成可追溯证据，比如：

```json
{
  "rule_name": "360分身导出包规则",
  "matched_features": [
    "应用名为稳定应用名+数字后缀",
    "同基础名成组出现",
    "APK不可安装",
    "文件大小异常"
  ],
  "manual_label": "分身导出包/无效样本",
  "evidence": "人工确认该类样本为360分身导出包，不作为普通恶意APP训练样本",
  "reviewer": "人工复核",
  "review_time": "2026-06",
  "affected_examples": ["MOMO陌陌5", "MOMO陌陌6", "MOMO陌陌7"]
}
```

这样以后系统可以自动引用：

```text
命中360分身导出包规则，因此CM 93分不能单独作为恶意定性依据。
```

这就叫“可追溯证据”。

它有三个好处：

1. 下次同类样本可以自动处理。
2. 大模型生成理由时有依据，不会乱编。
3. 以后复盘时能知道为什么当时这么判。

一句话：

```text
人工经验不能只停留在人工脑子里，要变成规则、标签、样例和证据字段。
```

更简单地总结：

```text
旧模型：
看到高分 -> 判风险
看到异常特征 -> 判风险
人工看完了但经验不容易复用

新系统：
先看样本是不是有效
再看是不是分身导出包
再看有没有真实恶意证据
最后把人工判断理由保存成规则和证据
```

所以这三句话背后的核心意思是：

**你的任务不是简单提高分类准确率，而是要让系统知道“为什么高分不一定恶意，为什么有些样本不能进训练集，为什么人工判断要变成可复用的证据”。**

> 既然之前的引擎我做了xgboost,为什么现在这个test1项目里面还要加上xgboost,需要改吗或者他的好处

不冲突，反而应该保留。之前引擎里用了 XGBoost，不代表现在 `test1` 里就不该再用。区别在于：**旧 XGBoost 是主判定模型；现在 test1 里的 XGBoost 更适合作为 Engine C 里的“结构化概率底座/快速通道”。**

**旧引擎里的 XGBoost 是什么作用**

旧方案大概是：

```text
APK静态/动态特征 -> 260维特征向量 -> XGBoost -> 黑/白
```

它主要解决：

```text
这个 APK 像不像恶意样本？
```

输出更偏：

```text
黑 / 白 / 概率
```

它是主角。

**现在 test1 里的 XGBoost 是什么作用**

现在你的系统不只是判断 APK 黑白，而是在做：

```text
360结果
CM结果
武汉黑白标签
人工标注
四智能体证据
分身包规则
大模型复核
```

所以现在 XGBoost 的定位应该变成：

```text
结构化特征概率模型
```

也就是它负责快速、稳定地回答：

```text
根据已有结构化字段，这个样本恶意概率是多少？
```

然后再交给 Engine C 综合：

```text
XGBoost概率
+ 规则命中
+ 武汉标签
+ 人工标签
+ 甲乙模型复核
+ 四智能体证据
-> 最终结论
```

所以不是重复造轮子，而是给新系统一个可靠的“数值判断核心”。

**为什么现在还需要 XGBoost**

1. **大模型不适合直接算最终分数**

大模型适合解释：

```text
为什么判疑似
冲突点是什么
建议人工复核什么
```

但它不适合长期稳定地做：

```text
score=0.8372
阈值=0.82
白样本误报率<=1%
```

XGBoost 更适合做稳定概率输出。

2. **XGBoost 适合结构化字段**

你的字段很多是结构化的：

```text
360 score
CM score
是否武汉黑样本
是否武汉白样本
是否分身包
是否不可安装
是否仿冒
权限数量
通联数量
病毒家族
涉诈类别
```

这些正是 XGBoost 擅长的东西。

3. **XGBoost 推理快**

大批量样本不可能每条都让大模型分析。

可以这样：

```text
XGBoost高置信恶意 -> 直接判恶意
XGBoost高置信白 -> 直接判白
中间/冲突样本 -> 进入大模型复核
```

这叫快速通道。

好处：

```text
快
稳定
省算力
少调用大模型
```

4. **XGBoost 可解释性比大模型好**

它可以输出：

```text
特征重要性
SHAP解释
哪些字段推高风险
哪些字段降低风险
```

这对你后续写报告、调规则很有帮助。

5. **XGBoost 可以学习“新规则的权重”**

比如：

```text
CM score=93
是否分身包
是否不可安装
武汉白样本
360白样本
```

模型可以学到：

```text
CM 93 不一定强恶意
分身包特征应该降低普通恶意概率
武汉黑样本权重很高
武汉白样本权重很高
```

这比人工写死：

```text
CM 93 加多少分
分身包扣多少分
```

更稳。

**那现在的 XGBoost 需要改吗**

需要改的是“定位”和“输入特征”，不是把它删掉。

我建议你不要让 XGBoost 只复刻旧引擎那套：

```text
APK静态/动态260维 -> 黑白
```

而是升级成：

```text
多源研判特征 -> 恶意概率
```

输入应该包括：

```text
360_score
360_type
cm_score
cm_type
cm_description_type
wuhan_label
manual_label_source
is_clone_suffix_group
is_uninstallable
size_abnormal
static_agent_score
threat_intel_agent_score
impersonation_agent_score
business_label_agent_score
ioc_count
high_risk_permission_count
fraud_category
virus_family
fake_app
platform
```

输出建议是：

```text
malicious_probability
benign_probability
invalid_clone_probability（如果做多分类）
```

如果暂时简单一点，就先做二分类：

```text
恶意 vs 非恶意
```

但长期最好做三类或四类：

```text
恶意
白样本
疑似/人工复核
分身导出包/无效样本
```

**XGBoost 在当前系统里的最佳位置**

建议放在这里：

```text
原始字段
-> 四智能体提证据
-> XGBoost / WEC 输出结构化概率
-> Engine C 融合规则和标签优先级
-> 大模型生成解释
```

也可以画成：

```text
360/CM/武汉/人工/APP字段
        ↓
    特征工程
        ↓
    XGBoost
        ↓
  概率 + 特征贡献
        ↓
 Engine C 综合裁决
        ↓
 大模型生成依据
```

**什么时候可以不用 XGBoost**

只有在这些情况下可以考虑不用：

```text
样本量非常少
字段很少
没有人工/武汉标签
只想做规则系统
只需要大模型写说明，不做自动批量判断
```

但你现在不是这种情况。你有大量 360/CM 样本、冲突样本、武汉黑白标签、人工标注，所以 XGBoost 很有价值。

**一句话结论**

不用删 XGBoost，也不应该删。

之前 XGBoost 是：

```text
旧引擎的最终黑白分类器
```

现在 XGBoost 应该变成：

```text
test1 系统里的结构化概率判断模块和高置信快速通道
```

它的好处是：

```text
稳定、快、可解释、适合结构化字段、能学习各类证据权重、能减少大模型调用、能提高冲突样本判断的准确性。
```

真正需要改的是：

```text
不要只用旧260维APK特征
而要加入360/CM结果、武汉标签、人工标签、分身包特征、四智能体证据分和业务字段。
```

这样 XGBoost 才是新系统的一部分，而不是旧模型的重复。

> 不是，我的意思是既然之前的引擎也有xgboost，我现在的项目也有xgboost，现在的比之前多的作用是什么

明白，你问的不是“为什么还要 XGBoost”，而是：

```text
旧引擎已经有 XGBoost；
现在 test1 也有 XGBoost；
那现在这个 XGBoost 比旧的 XGBoost 多了什么作用？
```

答案是：**旧 XGBoost 只是单一黑白分类器；现在的 XGBoost 是整个研判系统里的“概率底座 + 快速通道 + 证据融合模块 + 大模型前置过滤器”。**

它不只是重复做黑白分类。

---

**1. 旧 XGBoost 的作用：直接判黑白**

旧引擎里的 XGBoost 大概是这样：

```text
APK静态/动态特征
-> XGBoost
-> 黑 / 白
```

它的输入主要是：

```text
权限特征
API调用特征
动态行为特征
文件大小
文件权限
字符串
So文件
```

它解决的是：

```text
这个 APK 像不像恶意样本？
```

输出是：

```text
恶意概率 / 黑白结果
```

也就是说，旧 XGBoost 本身就是最终判定核心。

---

**2. 现在 XGBoost 的作用 1：融合 360 和 CM 的结果**

现在的 XGBoost 不只是看 APK 自身特征，还可以看：

```text
360 类型
360 score
CM 类型
CM score
CM description
两个引擎是否冲突
冲突类型是什么
```

这在旧 XGBoost 里没有。

比如旧模型只知道：

```text
权限有风险
```

现在模型可以知道：

```text
360=白
CM=疑似
CM score=93
CM理由=存在获取用户手机敏感信息风险
```

它可以学习：

```text
这种 CM 93 不一定是强恶意
```

这就是新增作用：**学习两个引擎之间的可信度关系。**

---

**3. 现在 XGBoost 的作用 2：吸收人工标注和武汉黑白标签**

旧 XGBoost 主要依赖历史黑白样本。

现在 XGBoost 可以加入：

```text
人工标注结果
武汉确认恶意
武汉确认白样本
人工标注来源
标签可信度
```

这让它不只是学习“APK像不像恶意”，而是学习：

```text
在我们这个业务口径下，什么样的样本最终应该判恶意/白/复核。
```

比如：

```text
CM=93
但武汉确认白
```

新 XGBoost 可以学到：

```text
武汉白样本权重高于 CM 93
```

旧 XGBoost 没这个能力，因为它没有这些标签来源字段。

---

**4. 现在 XGBoost 的作用 3：识别特殊样本状态**

旧 XGBoost 通常只分：

```text
黑 / 白
```

现在你需要识别：

```text
真实恶意APP
白样本
疑似样本
360分身导出包
不可安装样本
无效样本
人工复核样本
```

尤其是：

```text
MOMO陌陌5/6/7
QQ1
蜂鸟众包1
快手1
```

这类“稳定应用名 + 数字后缀”的分身包。

新 XGBoost 可以加入特征：

```text
is_clone_suffix_group
same_base_name_count
is_uninstallable
size_abnormal
```

于是它可以学习：

```text
这类样本即使 CM=93，也不应按普通恶意APP处理。
```

旧 XGBoost 没有这个样本状态层，只会把它当普通 APK 分类。

---

**5. 现在 XGBoost 的作用 4：给 Engine C 提供概率，不单独最终裁决**

旧 XGBoost 输出之后，基本就是结论。

现在 XGBoost 输出的是：

```text
malicious_probability
```

然后还要交给 Engine C：

```text
XGBoost 概率
+ 标签优先级
+ 分身规则
+ 四智能体证据
+ 模型甲乙复核
+ 人工/武汉标签
-> 最终结论
```

也就是说，现在 XGBoost 是“证据之一”，不是唯一判官。

这能避免旧模型的问题：

```text
模型错了 -> 最终就错了
```

现在可以被规则、人工标签、武汉标签或模型甲乙纠偏。

---

**6. 现在 XGBoost 的作用 5：做高置信快速通道**

这是新系统很大的工程价值。

现在可以这样用：

```text
XGBoost 置信度很高
且没有冲突
且没有分身包/无效样本特征
-> 直接输出
```

只有这些样本才进入大模型：

```text
360和CM冲突
XGBoost概率在边界区
命中分身包规则
证据不足
武汉标签和引擎冲突
```

旧 XGBoost 没有“大模型前置过滤器”的角色。

现在它可以帮你：

```text
减少大模型调用
提升批量处理速度
降低成本
保证简单样本稳定输出
```

---

**7. 现在 XGBoost 的作用 6：为大模型提供可解释输入**

旧 XGBoost 可能只输出一个分类结果。

现在可以输出：

```text
概率
重要特征
SHAP贡献
哪些因素推高风险
哪些因素降低风险
```

然后大模型根据这些生成报告：

```text
该样本 CM 给 93 分，但主要风险来自敏感信息获取；
同时命中 360 分身导出包规则，因此不建议直接判恶意。
```

也就是说，XGBoost 不只是判断，还给大模型提供“证据骨架”。

---

**8. 现在 XGBoost 的作用 7：学习冲突样本的裁决模式**

这是旧引擎没有的关键能力。

你的数据里共同 MD5 有：

```text
108,989 条
```

冲突有：

```text
83,649 条
```

最大冲突是：

```text
360白 + CM疑似 = 76,660 条
```

旧 XGBoost 不知道这个冲突结构。

现在 XGBoost 可以专门学习：

```text
360白 + CM疑似93 + 敏感信息风险
最终多数应进入疑似/复核/非恶意

360白 + CM恶意100 + 明确色情/贷款/博彩诈骗
最终更可能是真恶意或高优先级复核

360恶意 + CM疑似
要看360病毒名和CM描述
```

这就是现在 XGBoost 相比旧 XGBoost 增加的最实际作用：

```text
学习“两个引擎冲突时该相信谁、该降级还是升级”。
```

---

**9. 一句话区别**

旧 XGBoost：

```text
APK特征 -> 黑白分类
```

现在 XGBoost：

```text
双引擎结果 + 人工/武汉标签 + 四智能体证据 + 特殊样本规则
-> 输出可校准概率
-> 参与 Engine C 综合裁决
-> 过滤大模型调用
-> 帮助解释冲突样本
```

```text
现在的 XGBoost 不是重复旧引擎，而是从“单一分类器”升级成“多源研判系统中的概率融合层”。
```

它比之前多的作用是：

```text

```

这才是现在项目里继续保留 XGBoost 的真正价值。

> 现在 XGBoost 训练的时候不应该加入以下这些，因为这是标签，不能加入到训练的特征中
> 人工标注结果
> 武汉确认恶意
> 武汉确认白样本
> 人工标注来源
> 标签可信度

对，你这个判断是对的。这里我之前说法需要收紧：**人工标注结果、武汉确认黑白、人工标注来源、标签可信度，不应该作为 XGBoost 的普通输入特征。**否则就是标签泄漏。

训练 XGBoost 时应该这样分：

**不能作为特征 X 的内容**

```text
人工标注结果
武汉确认恶意
武汉确认白样本
人工标注来源
标签可信度
final_label
人工审核结果
```

这些本质上是“答案”或“答案来源”。如果放进特征，模型会学到：

```text
看到 wuhan_white=1 -> 判白
看到 manual_malicious=1 -> 判恶意
```

验证集、测试集指标会虚高，但真实泛化能力没有意义。

**它们应该怎么用**

这些字段应该用于构造标签 y、样本权重、数据划分和评估分层。

例如：

```text
人工标注恶意 -> y=1
人工标注白 -> y=0
武汉确认恶意 -> y=1
武汉确认白 -> y=0
冲突未标注 -> 不进训练
分身/不可安装 -> 单独类别或排除
```

`标签可信度` 可以用作训练权重，而不是特征：

```text
人工标注样本 weight = 1.0
武汉确认样本 weight = 0.9
双引擎一致弱标签 weight = 0.4
```

也就是说：

```text
X = 样本自身特征 + 引擎检测特征
y = 人工/武汉/可信标签生成的答案
weight = 标签来源可信度
```

**可以作为 XGBoost 特征的内容**

可以放进 X 的是推理时真实可获得、且不是答案本身的字段：

```text
360_score
360_type
360_virus_name
cm_score
cm_type
cm_description
cm_virus_name
两个引擎是否冲突
冲突类型
appName特征
pkgName特征
size
size_abnormal
是否数字后缀
同基础名样本数量
是否疑似分身包
是否不可安装
权限数量
高危权限数量
SDK特征
通联域名/IP数量
是否有IOC
是否仿冒
证书特征
平台类型
文件类型
```

尤其是：

```text
is_clone_suffix_group
size_abnormal
installable_status
```

这些不是标签，是样本客观特征，可以作为模型输入。

**武汉标签什么时候能用**

这里要分两种情况。

如果你的目标是训练一个独立模型：

```text
不给模型武汉答案，只让模型靠样本字段判断
```

那武汉确认黑白只能作为 y，不能作为 X。

如果你的线上系统推理时本来就会实时查询武汉接口，并且业务上允许“武汉黑白”作为外部高可信规则，那它可以放在 Engine C 的规则层里：

```text
武汉确认白 -> 规则优先判白或降权
武汉确认恶意 -> 规则优先判恶意或高优先级复核
```

但这不是 XGBoost 学出来的能力，而是外部知识库/规则融合。

所以更稳的架构是：

```text
XGBoost：
只吃样本特征 + 360/CM检测特征
输出 malicious_probability

标签系统：
人工/武汉标签用于训练 y 和样本权重

Engine C：
在 XGBoost 概率之外，再融合武汉黑白、人工库、规则命中
```

**修正后的说法**

现在 XGBoost 比旧 XGBoost 多的作用，不应该说“把人工/武汉标签作为输入特征”，而应该说：

```text
用人工/武汉标签构造更可靠的训练目标；
用360/CM结果和样本字段作为输入特征；
让模型学习不同检测信号、样本形态和冲突类型与最终标签之间的关系。
```

一句话：

**人工和武汉是答案来源，不是普通特征；它们训练 XGBoost 的 y 和 sample_weight，不能直接喂给模型当 X。**
